> 面向维护者，重点是**契约、约束与未验证项**，而非操作步骤（操作见 `docs/使用指南.md` §3.2/§5）。

## 1. 改造前的问题

原实现要求部署侧额外提供一个 PostgreSQL，并在运行期注入 `DATABASE_URL`：

- 服务启动强依赖一个必须存在、必须可连、必须与镜像内客户端版本兼容的外部组件；
- `Dockerfile` 与 `charts/values.yaml` 都注明 `DATABASE_URL` 无默认值兜底，留空则容器反复重启；
- `docker/entrypoint.sh` 只做「等外部 PG 就绪」，等待逻辑与被等待对象的生命周期是分离的。

改造后：**一个容器即自洽启动**，数据库随容器内嵌，数据落在节点本地挂载目录。

## 2. 选型结论：为什么是 PostgreSQL，不是 SQLite

代码对 PG 特性的依赖很深，换 SQLite 的代价被严重低估：

| 依赖的 PG 能力 | 位置 | SQLite 侧代价 |
|---|---|---|
| `UUID DEFAULT gen_random_uuid()` 主键（7 张表） | `db_migration.py` | 无 uuid 类型，需改 Python 侧生成并调整 DAO 取值 |
| `JSONB`（cards / level*_config / formula_lines / details） | 建表 + `dao` | 退化为 TEXT，DAO 的类型兼容分支要反过来重写 |
| `ALTER TABLE ... ADD/DROP COLUMN IF NOT EXISTS` | `db_migration.py` 共 30 条 | SQLite 完全不支持 `IF NOT EXISTS`，需 PRAGMA 探测 + 动态 SQL |
| `CREATE INDEX IF NOT EXISTS` | 6 条 | 同样不支持，需查 `sqlite_master` |
| `UUID REFERENCES ...` 外键 + `ON DELETE CASCADE` | 建表 | 需显式 `PRAGMA foreign_keys=ON` |
| 行级 MVCC + 多连接写 | `db.py` 连接池 + SSE 多线程 | 库级写锁，多会话并发会碰 `database is locked` |

其中 `ON CONFLICT ... DO UPDATE SET x=EXCLUDED.x` 与 `RETURNING` 是唯一能复用的部分。**结论：保留 PostgreSQL。**

备选方案评估：
- **DuckDB**：分析型引擎，与本项目「短事务 KV 式读写」的负载形态不符；
- **MySQL/MariaDB**：多一个网络端口与安装体积，但换不到本项目需要的任何东西；
- **外部 PG 保持现状**：没解决「多一个必须存在的组件」这个原始痛点。

## 3. 改造后的架构

```
容器内                                    节点侧
─────────────────────────────────────     ──────────────────────
/home/aicm                                /data/aicm
├── workspace            (挂载点)   <───   └── workspace
│   └── <task_id>/       仿真产物（持久化）
├── db                   (挂载点)   <───   └── db
│   ├── data             PGDATA             └── data/  run/
│   │   └── PG_VERSION   =14（版本守卫比对）      （initdb 产出，持久化）
│   └── run              Unix socket
│       └── .s.PGSQL.5432    localhost only
└── run.py 等            仿真工具本体（随镜像，不被挂载遮蔽）
```

两个挂载点**统一在容器内 `/home/aicm` 下**，节点侧各给一个独立目录，路径一一对应。
容器内父目录 `/home/aicm` 本身不被整体挂载，只是两个子目录各自挂载，
因此仿真工具本体（`/home/aicm/run.py` 等）仍在镜像层里，不受挂载影响。

> 后续修正：若 `/home/aicm` 被**整目录**挂载，工具目录与挂载点同名会直接把镜像层里的
> 工具代码遮掉（工具被迫落到宿主机）。当前布局已把**数据挂载树**移出 `/home/aicm`，
> 统一放到 `/home/data` 下（workspace/db），仿真工具保持镜像内 `/home/aicm` 不动 ——
> 工具目录与挂载路径分置，整目录挂载不会再遮掉工具（见 Dockerfile 的 mkdir 与 ENV
> `AICM_MCP_SIM_TOOL_HOME` / `AICM_MCP_WORKSPACE_ROOT` / `SQLITE_PATH`）。

- **连接走 Unix socket、不开 TCP**：`DATABASE_URL=postgresql://postgres@/equivalent_modeling_service?host=/home/aicm/db/run`。
  与端口占用、`HOSTNAME` 解析、`listen_addresses` 全部解耦。
- **启动链**（`docker/entrypoint.sh`）：
  `workspace 自检 → DB 目录自检 → 版本守卫 → 空目录 initdb → setsid 启动 postgres → pg_isready 就绪探测 → 建库 → 业务进程 → 退出时 pg_ctl stop -m fast`
- **进程模型**：PG / MCP / Flask 三进程同容器，沿用原有「任一退出则整体退出 + trap 连带回收」模式。

## 5. 关键设计决策与理由

| 决策 | 理由 |
|------|------|
| 钉死 `postgresql-14` | Ubuntu 22.04 官方源只有该主版本。**PGDATA 与主版本强绑定**，浮动包名会让某次重建后旧数据目录直接拒绝启动 |
| 不 `CREATE EXTENSION` | `gen_random_uuid()` 自 PG 13 起内建；`postgresql-contrib` 未安装，避免引入新依赖 |
| PGDATA 放在挂载点的 `data/` 子目录 | 挂载点本身可能被 initContainer `chown`，而 PG 对数据目录权限敏感；隔离一层更稳 |
| `shared_buffers=64MB` | 对齐容器默认 `--shm-size=64MB`，避免 `could not resize shared memory segment` |
| `max_connections=20` | 对齐 `app/db.py` 的 `minconn=2 / maxconn=10` |
| socket 而非 TCP | 不占端口、不怕同 Pod 内端口冲突、不需要 `listen_addresses` |
| `pg_ctl stop -m fast`（不用 `immediate`） | `immediate` 等于 `kill -9`，下次启动走 crash recovery，极端情况丢已提交事务 |
| DB 目录自检**不可豁免**（`docker run` 默认路径） | 数据库静默落在镜像层里意味着容器重建即丢全部会话历史，代价高于丢仿真产物。仅本地验证可用 `DB_ALLOW_LOCAL=1` |
| 保留 `DATABASE_URL` 覆盖能力 | 集群 Secret 仍可注入 TCP 串，**同一个镜像同时支持内嵌与外部 PG 两种模式**，构成回退逃生门 |

## 8. 运维须知（务必转达部署侧）

1. **必须挂载 `/home/aicm/db`**（节点侧建议 `/data/aicm/db`），否则容器直接启动失败 —— 这是有意的强制。
2. **该目录必须落在节点本地磁盘**，**不能**用 NFS。PG 依赖本地文件锁与 `fsync` 语义。
3. **`replicas` 必须为 1**。PGDATA 是单写者，两个 Pod 同时打开同一目录会损坏数据。
4. **Pod 漂移到其他节点会看到「空」数据库**（与 `sim-workspace` 同源的失效模式）。需要跨节点保留数据必须换持久卷方案，但**不能用 NFS**。
5. **PG 主版本升级只能走** `pg_dumpall` → 换镜像 → 空目录 `initdb` → 恢复；直接复用老数据目录会被版本守卫拦下。
6. **删掉 `/data/aicm/db` 等于删库**，无二次确认。

## 9. 回退路径

改动的设计保留了逃生门：`charts/values.yaml` 中取消注释 `secrets.databaseUrl` 并填入外部 PG 连接串，
即可让**同一个镜像**回到「连外部 PostgreSQL」模式，无需重新构建。此时容器内的内嵌 PG 仍在运行但未被使用
（可接受，若需彻底停用应另做开关）。
