# TrainMesh Agent 使用指南

## 1. 产品概述

TrainMesh Agent 是一款面向 AI 训练组网仿真测试的智能助手系统。它帮助测试人员：

- **输入组网参数** — 设备类型 (A2/A3/A5)、并行策略 (DP/TP/PP)、模型架构参数
- **生成组网拓扑** — 可视化原始组网与等效组网的 Mesh 结构
- **构建模型结构** — 自动生成 Transformer 模型层级描述
- **推送等效分析** — 逐条展示等效策略、计算指标与公式
- **执行仿真验证** — 通过 MCP 客户端下发仿真任务、实时监控进度
- **等效性判定** — 自动对比原始组网与等效组网仿真结果，输出结论

系统采用 **Flask 后端 + 静态前端 + OpenAI LLM + MCP 仿真** 的四层架构。

## 2. 系统架构

```
┌──────────────┐     SSE/REST/WS      ┌──────────────────────┐     JSON-RPC      ┌─────────────┐
│  前端 (SPA)   │ ──────────────────→ │  Flask Agent 后端     │ ──────────────→ │ MCP 仿真服务 │
│  index.html   │                      │  orchestrator + skills│                  │  (端口 9000) │
└──────────────┘                      └──────────────────────┘                  └─────────────┘
                                            │          │
                                      OpenAI API     PostgreSQL
                                      (LLM 推理)     (持久化)
```

核心组件：

| 目录 | 功能 |
|------|------|
| `app/routes/` | REST/WebSocket 路由（session、chat、simulation、model_catalog） |
| `app/agent/` | Agent 编排：orchestrator（LLM 驱动循环）、session（状态管理）、guardrails（护栏校验） |
| `app/skills/` | 注册式技能：组网生成、模型生成、仿真分析 |
| `app/mcp/` | MCP 客户端：JSON-RPC 调用仿真系统的任务下发/状态查询/结果获取 |
| `app/models/` | Pydantic 数据模型 + 模型目录（HuggingFace 远程解析） |
| `app/dao/` | PostgreSQL 数据访问层 |
| `static/` | 前端单页应用（HTML/CSS/JS + 拓扑渲染 + 仿真数据流） |

### 3.2 PostgreSQL 数据库

系统支持两种数据库运行形态，由 `DATABASE_URL` 选择：

| 形态 | 使用场景 | 连接串 |
|------|----------|--------|
| **内嵌（容器镜像）** | 生产 / K8s 部署 | `postgresql://postgres@/train_mesh_agent?host=/home/aicm/db/run`（镜像 ENV 默认值，走 Unix socket，不开 TCP） |
| **外部 / 本机** | 本地开发、既有外部 PG | `postgresql://postgres:postgres@127.0.0.1:5432/train_mesh_agent`（`app/config.py` 默认值） |

**本地开发**（连本机已安装的 PostgreSQL）：

```sql
CREATE DATABASE train_mesh_agent;
```

**容器内嵌模式**（无需手工建库，entrypoint 自动完成）：

```bash
# 节点侧先准备好持久化目录并交出属主（容器以 uid 1000 运行）
sudo mkdir -p /data/aicm/db && sudo chown 1000:1000 /data/aicm/db

docker run -d --name train-mesh-agent \
  -v /data/aicm/workspace:/data/aicm/workspace \
  -v /data/aicm/db:/home/aicm/db \
  -p 5000:5000 <image>
```

启动时 `docker/entrypoint.sh` 会按顺序完成：目录自检 → PG 版本守卫 → 空目录 `initdb` → 拉起 `postgres` → 建库 `train_mesh_agent` → 启动业务进程。整个过程不需要人工介入。

应用启动时自动执行建表迁移（`app/db_migration.py`），创建以下表：

| 表 | 用途 |
|----|------|
| `sessions` | 会话（步骤、任务 ID） |
| `topology_params` | 拓扑参数（DP/TP/PP、模型维度） |
| `simulation_params` | 仿真脚本与配置 |
| `simulation_results` | 仿真结果（cards JSON） |
| `comparison_reports` | 等效性对比报告 |
| `conversation_messages` | 对话消息记录 |
| `model_catalog` | 模型架构参数目录 |

所有主键均为 UUID（`gen_random_uuid()`，PG 13+ 内建，**不需要** `uuid-ossp` 或 `pgcrypto` 扩展），`IF NOT EXISTS` 保证重复执行安全。迁移结束时会对核心表与关键列做一次硬校验，缺失即让容器启动失败，不会以「半可用」状态带病运行。

#### 内嵌数据库的持久化契约与约束

| 项 | 值 / 约束 |
|----|-----------|
| 容器内数据目录 | `/home/aicm/db`（挂载点），`PGDATA=/home/aicm/db/data`，socket 在 `/home/aicm/db/run` |
| 节点侧目录 | `/data/aicm/db`（`charts/values.yaml` 的 `database.nodePath`） |
| 挂载要求 | **必须是挂载点**。`docker/check_db.py` 会在启动时校验，未挂载直接 `exit 1` —— 绝不能容忍数据库静默写进镜像层（容器重建即丢全部会话历史） |
| 属主 / 权限 | 属主必须是容器运行用户（uid 1000）；`PGDATA` 权限必须是 `0700`（PG 对此敏感）。K8s 下由 initContainer `chown` 保证 |
| 主版本锁 | 镜像内为 **PostgreSQL 14**（Ubuntu 22.04 官方源唯一的 PG 主版本）。`PGDATA` 与主版本强绑定，`entrypoint.sh` 启动前会比对 `PG_VERSION`，不一致即带明确提示退出 |
| 存储介质 | 必须落在**节点本地磁盘**。**不能**放 NFS —— PG 依赖本地文件锁与 `fsync` 语义 |
| 多副本 | 禁止。数据目录是单写者，两个 Pod 同时打开同一 `PGDATA` 会损坏数据（与 `sim-workspace` 的失效模式一致，`replicas` 必须为 1） |

> **升级数据库主版本的唯一路径**：旧容器内 `pg_dumpall` → 换新镜像 → 用**空**数据目录启动（自动 `initdb`）→ `psql` 恢复。任何「直接换镜像复用老数据目录」的做法都会被版本守卫拦下。

### 3.3 MCP 仿真服务

TrainMesh Agent 通过 MCP 协议与独立仿真系统通信。仿真服务需先启动并在指定端口提供以下工具：

| MCP 工具 | 说明 |
|----------|------|
| `execute_task` | 下发仿真任务，返回 `task_id` |
| `report_status` | 查询任务状态与进度 |
| `sync_logs` | 增量同步仿真日志 |
| `get_result` | 获取完整仿真结果 |
| `card_detail` | 获取每卡仿真指标 |
| `get_device_detail` | 获取设备算子追踪与时间线 |
| `get_hbm_detail` | 获取 HBM 使用量拆解 |
| `get_comm_detail` | 获取 TP/PP/DP 通信详情 |

## 5. 启动服务

**本地开发**（依赖本机 PostgreSQL 与 MCP 仿真服务）：

```bash
# 确保 PostgreSQL 和 MCP 仿真服务已启动
python -m app.main
```

或直接运行：

```bash
python app/main.py
```

**容器方式**（数据库随容器内嵌，无需外部 PG）：

```bash
docker run -d --name train-mesh-agent \
  -v /data/aicm/workspace:/data/aicm/workspace \
  -v /data/aicm/db:/home/aicm/db \
  -p 5000:5000 <image>
```

容器启动即自动完成 `initdb` → 建库 → 建表，日志中可见 `[entrypoint]` 各阶段进度（见 §3.2）。两个挂载目录都**必须有**，缺失时容器会明确报错退出，而不是静默把数据写进镜像层。

服务启动后访问 `http://localhost:5000` 即可打开前端界面。

> 只做本地验证、暂不想挂载数据目录时，可加 `-e DB_ALLOW_LOCAL=1` 豁免数据库目录的挂载点自检（会打印醒目告警；`/data/aicm/workspace` 一侧同理可用 `AICM_MCP_WORKSPACE_ALLOW_LOCAL=1`）。

## 7. 工作流程

Agent 驱动四步工作流，每步等待用户确认后推进：

### Step 1 — 等效参数设定

1. 用户输入组网参数（设备类型、DP/TP/PP）和模型名称
2. **模型参数自动填充**：Agent 调用 `auto_fill_model_params`，通过 HuggingFace → ModelScope → 内置表的四级解析链获取模型架构参数 (L/H/A/dff/V)，推送到前端表单
3. 护栏静默校验参数合法性
4. 调用 `training-mesh-gen-skill` 生成原始组网拓扑
5. 调用 `training-model-gen-skill` 生成原始模型结构
6. 前端渲染组网图 + 模型层级图

### Step 2 — 等效计算推导

1. 用户确认等效计算
2. Agent 逐条推送等效策略、计算指标、公式（`emit_formula_line`），前端逐行渲染
3. 计算等效组网参数（调整 PP/DP/层数等）
4. 生成等效组网拓扑 + 等效模型结构
5. 前端渲染等效组网图

### Step 3 — 等效仿真验证

1. 用户确认下发仿真
2. MCP 客户端下发仿真任务（原始 + 等效）
3. WebSocket 实时推送仿真状态与进度
4. 仿真完成后获取每卡指标（FLOPs、HBM、TP/PP/DP 通信量）

### Step 4 — 等效方案输出

1. 自动对比原始与等效仿真结果
2. 计算各指标差异百分比（容忍度 5%）
3. 输出等效性结论：✅ 通过 或 ❌ 不通过

## 8. 模型参数解析

模型架构参数的获取采用四级解析链（`resolve_model_config`）：

| 级别 | 来源 | 说明 |
|------|------|------|
| 1 | PostgreSQL `model_catalog` | 已入库模型（管理端新增 + 远程导入 + 启动种子） |
| 2 | 本地 JSON 缓存 | `.model_cache/` 目录下的离线缓存文件 |
| 3 | 远程获取 | HuggingFace → ModelScope（完整仓库 ID 直接获取；裸名通过 HF 搜索匹配） |
| 4 | 内置模糊匹配 | 离线兜底表（Qwen3-32B、LLaMA 系列等） |

**仅支持稠密模型**。MoE/稀疏模型（Mixtral、DeepSeek-V2/V3 等）会被检测并标记为 `model_type=sparse`，前端收到后提示不支持。

## 9. 护栏校验

输入护栏（`validate_input_params`）在 Agent 调用工具时静默执行：

- **设备类型**：仅允许 A2、A3、A5
- **DP 范围**：1–1024（>512 发警告）
- **TP 范围**：1–32（非 2 的幂次发警告）
- **PP 范围**：1–128
- **总节点数**：= DP × TP × PP，>10000 发警告

输出护栏（`validate_topology_output`）校验生成拓扑的一致性：

- 节点数 = `total_nodes` = DP × TP × PP
- 通信域分组大小与并行度匹配

## 11. 数据模型概览

### 会话状态 (`SessionState`)

```
session_id          — 会话标识 (8字符 UUID)
step                — 当前阶段: idle | params_collected | equiv_calculating | equiv_generated | simulating | completed
original_params     — 原始拓扑参数
equivalent_params   — 等效拓扑参数
original_topology   — 原始组网拓扑 (MeshTopology)
equivalent_topology — 等效组网拓扑
original_training_model   — 原始模型结构 (TrainingModel)
equivalent_training_model — 等效模型结构
original_simulation  — 原始仿真结果 (SimulationResult)
equivalent_simulation — 等效仿真结果
comparison_report   — 对比报告 (ComparisonReport)
simulation_params   — 仿真配置 (SimulationParams)
history             — 对话历史
```

### 组网拓扑 (`MeshTopology`)

```
name             — 组网名称
device_type      — A2 / A3 / A5
total_nodes      — 总节点数 = DP × TP × PP
dp_size / tp_size / pp_size
nodes            — 节点列表 (MeshNode: id, device_type, dp_rank, tp_rank, pp_rank, global_rank)
communication_groups — 通信域分组 {dp: [...], tp: [...], pp: [...]}
```

> **Rank 布局（与仿真系统一致，TP-DP-PP）**：`global_rank = pp_rank*(tp*dp) + dp_rank*tp + tp_rank`
> 即 TP 最低位、DP 居中、PP 最高位。唯一实现见 `app/rank_layout.py`，前端镜像见
> `static/topo-renderer.js` 的 `meshRankOf` / `meshDecomposeRank`。转换函数：
> ```
> tp_rank = global_rank % tp
> dp_rank = (global_rank // tp) % dp
> pp_rank = global_rank // (tp * dp)
> ```

### 每卡指标 (`CardMetrics`)

```
card_id / global_rank
flops_per_card   — 单卡 FLOPs
hbm_gb           — HBM 总占用
hbm_model_gb     — 模型显存占用 (权重+梯度+优化器)
tp_comm_gb_per_micro  — TP 通信量
pp_comm_mb_per_micro  — PP 通信量
dp_comm_gb_per_step   — DP 通信量
```

### 等效性报告 (`ComparisonReport`)

```
flops_diff_pct / hbm_diff_pct / tp_comm_diff_pct / pp_comm_diff_pct / dp_comm_diff_pct
is_equivalent    — 是否等效 (所有指标差 ≤ 5%)
error_tolerance_pct — 容忍度阈值 (默认 5%)
details          — {conclusion: "✅/❌", max_diff_pct: ...}
```

## 12. 常见问题

### Q: 启动时报数据库连接失败

先判断当前是哪种形态：

**内部 / 本机模式**：确保 PostgreSQL 已启动，且 `DATABASE_URL` 配置正确。连接池默认 2–10 连接（`app/db.py`），建池带有限重试（`DB_CONNECT_RETRIES`，默认 10 次 × 1.5s），日志里会打印连接目标与 `PGDATA`。

**容器内嵌模式**：按顺序排查下面几条，日志中每一步都有 `[entrypoint]` / `[db-check]` / `[wait_for_db]` 前缀：

| 现象 | 原因 | 处理 |
|------|------|------|
| `not a mount point` 并退出 | `/home/aicm/db` 未挂载 | 按 §5 加 `-v /data/aicm/db:/home/aicm/db`；K8s 检查 `database.nodePath` 与 hostPath 卷 |
| `权限为 0755，PostgreSQL 要求数据目录为 0700` | 挂载点权限被宿主机覆盖 | `sudo chmod 700 <nodePath>/data`（首次由容器内 `initdb` 自行创建，一般不会遇到） |
| `属主 uid=0 与容器运行用户 uid=1000 不一致` | 宿主机目录由 root 创建 | `sudo chown -R 1000:1000 <nodePath>`；K8s 下由 initContainer 自动完成 |
| `FATAL: PGDATA 版本(18) 与镜像内 PostgreSQL(14) 不一致` | 复用了其他主版本的数据目录 | 走 §3.2 的 dump/restore 升级路径，不要强行复用 |
| `initdb 失败` | 挂载目录不可写 | 确认属主/权限，并确认磁盘未满 |
| `等待 PostgreSQL 就绪超时` | 进程起不来或 `--shm-size` 过小 | 查看 `postgres` 自身输出的崩溃原因；必要时加大 `--shm-size`（当前 `shared_buffers=64MB`） |
| `数据库 schema 不完整，拒绝以半可用状态启动` | 建表迁移有失败项 | 报错里会列出缺失的表/列与失败语句；常见于库或用户名缺少 DDL 权限 |

手动检查数据的两种方式：

```bash
# 只做就绪探测
docker exec <container> pg_isready -h /home/aicm/db/run -U postgres -d train_mesh_agent

# 进 psql（socket 模式，无需口令）
docker exec -it <container> psql -h /home/aicm/db/run -U postgres -d train_mesh_agent -c '\dt'
```

### Q: 模型参数填充失败

1. 检查网络是否可访问 HuggingFace (`huggingface.co`)
2. 尝试使用完整仓库 ID（如 `Qwen/Qwen2.5-7B`）而非裸名
3. 裸名会先搜索 HF 匹配官方仓库，再走远程获取
4. 最终兜底为内置种子表

### Q: 仿真任务下发失败

1. 确认 MCP 仿真服务已在 `MCP_SERVER_URL` 端口启动
2. 检查服务健康状态：`GET <MCP_SERVER_URL>/health`
3. 查看 Agent 日志中的 MCP 调用错误信息

### Q: MoE 模型无法使用

当前仅支持稠密模型。系统会自动检测 MoE/稀疏模型（Mixtral、DeepSeek-V2/V3、Qwen-MoE 等）并返回 `model_type=sparse`，前端提示不支持。

### Q: 如何手动新增模型到目录

通过 API 新增：

```bash
curl -X POST http://localhost:5000/api/model-catalog \
  -H "Content-Type: application/json" \
  -d '{
    "model_name": "MyModel-10B",
    "num_layers": 40,
    "d_model": 5120,
    "num_heads": 40,
    "d_ffn": 13824,
    "vocab_size": 32000,
    "description": "自定义稠密模型"
  }'
```

或从 HuggingFace 导入：

```bash
curl -X POST http://localhost:5000/api/model-catalog/fetch \
  -H "Content-Type: application/json" \
  -d '{"model_name": "meta-llama/Llama-2-7b-hf"}'
```

### Q: 如何重置内置模型种子

```bash
curl -X POST http://localhost:5000/api/model-catalog/seed
```

## 13. 开发与扩展

### 新增 Skill

在 `app/skills/` 下创建目录，继承 `SkillBase`，实现 `execute()` 方法，注册到 `registry`：

```python
# app/skills/my-new-skill/__init__.py
from app.skills.base import SkillBase, SkillContext, SkillResult

class MyNewSkill(SkillBase):
    name = "my-new-skill"
    description = "新技能描述"

    def execute(self, args: dict, context: SkillContext) -> SkillResult:
        # 实现逻辑
        return SkillResult(success=True, data=result)
```

Skill 会自动出现在 Agent 的工具列表中。

### 新增护栏规则

修改 `app/agent/guardrails.py` 中的 `validate_input_params` 或 `validate_topology_output`。

### 新增 API 端点

在 `app/routes/` 下创建 Blueprint，注册到 `app/main.py` 的 `create_app()` 中。

### 数据库增量补丁

在 `app/db_migration.py` 的 `SCHEMA_SQL` 中追加 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 或 `CREATE INDEX IF NOT EXISTS`，应用启动时自动执行。

两点约定：

1. **不要**把一次性历史清理写成 `ALTER TABLE ... DROP COLUMN IF EXISTS`。这类语句每次启动都会重新执行（白拿表锁），需要清理旧库时手工执行一次即可。
2. 新增「关键表/列」时，同步把表名加到 `REQUIRED_TABLES`、把最容易被漏掉的列加到 `REQUIRED_COLUMNS`。收尾硬校验靠这两个元组判断 schema 是否完整——漏加会让校验形同虚设。
